# HELIOS — Crew Health Monitor

A prototype of on-board health monitoring software for long-duration missions. It collects
physiological, behavioral and environmental indicators, compares each one with the astronaut's
**own preflight baseline**, and turns any deviation into an explained finding with concrete steps.
Astronauts can then act on their health without waiting for a 14-minute-each-way ground loop.

> Prototype: all sensor data is simulated. This is not a medical device.

## Run it

No build step and no dependencies. It runs fully offline, as it would on board.

```bash
python3 -m http.server 8173
```

Then open http://localhost:8173. Opening `index.html` directly also works.

## What it does

Run `npm start` (or the command above) and open http://localhost:8173.

| Screen | Purpose |
|---|---|
| **My health** | Readiness score, six health-domain cards, ranked findings with "do now" steps, today's tasks, cabin environment, ground-link latency |
| **Trends** | Per-indicator charts against your personal normal range, limits and mission events; deviation, trend per week, 14-day projection, data coverage |
| **Daily check-in** | Two-minute self-report: sleep, mood, energy, stress, symptoms, manual vitals, privacy choice. Results are re-evaluated immediately |
| **Alertness test** | PVT-B psychomotor vigilance test (1 or 3 min), scored for mean RT, lapses (>355 ms) and false starts |
| **Protocols** | Ten on-board procedures (SPE shelter, sleep recovery, CO₂ headache, bone countermeasures, immune, SANS…) with step tracking and escalation criteria |
| **Downlink report** | Compact summary for the flight surgeon: queue for the next window, export JSON, or print |
| **Crew (CMO)** | Crew Medical Officer overview. Private behavioral entries stay hidden |

| **Model validation** | Results on real Inspiration4 crew blood data (see below) |

Across the app:

- **Cinematic interface:** animated deep-space starfield, a start-up sequence, glass panels and staggered entrance animations. Motion is turned off for anyone who prefers reduced motion.
- **Mission trajectory:** the Earth-to-Mars transfer arc with the vehicle's position, days to arrival and signal delay.
- **Body status map:** a body silhouette with pulsing hotspots per health domain; click one to open its trends.
- **Voice briefing:** a spoken summary of readiness, top findings and due tasks (Web Speech API, works offline).
- **Command palette:** press ⌘K, Ctrl+K or `/` to jump to any view, indicator, protocol or crew member, or run an action.
- **Sleep-period display** (moon icon): a red-shifted, low-blue-light theme.

## Feature modules

New capabilities live in `js/features/` and plug into the app via a small API (`H.app`) and event bus (`H.bus`), so `app.js` stays the shell.

| **Lab panels** (`labs.js`) | Enter blood count + metabolic panels; the 8 clinical-panel models validated on Inspiration4 data (`js/lab-model.js`, generated by `tools/evaluate.js`) score the latest draw against your own preflight draws. "Load real example" loads an actual Inspiration4 crew member's draws. |
| **Import wearables** (`wearables.js`) | Apple Health `export.xml` (streamed, works with large exports) and any CSV from Fitbit, Garmin, Oura, Whoop or a spreadsheet — columns and units are auto-matched, then confirmed. |
| **What works for you** (`outcomes.js`) | Logging a protocol snapshots its target indicators; 2–7 days later HELIOS checks whether they improved and keeps a per-person track record. |
| **Symptom triage** (`triage.js`) | Offline yes/no guides — chest pain, vision change, head injury, burns, allergic reaction — ending in steps and the kit items needed. |
| **Medical kit** (`medkit.js`) | Shared inventory with expiry in mission days, radiation-sensitive and prescription flags, a stock forecast (planned or actual use, whichever is higher) and a per-person medication log. |
| **Day planner** (`planner.js`) | 24-hour circadian plan (light, caffeine, peak work, nap, exercise, wind-down, sleep), adjusted to your sleep debt and alertness results. |
| **Cognition tests** (`cognition.js`) | Digit span (working memory) and math processing (speed), compared with your own history, alongside the PVT. |
| **Nutrition & hydration** (`nutrition.js` + engine) | New health domain: body mass, fluid and energy intake, with its own rule and protocol P-NUT-01. |
| **Space weather** (`spaceweather.js`) | Solar-particle-event warning with countdown, storm-shelter timer and dose received / avoided. |
| **Weekly trends** (`weekly.js` + `js/weekly.js`) | Multi-week trend detection. Readings are averaged per mission week, and the last 8 complete weeks are tested for slow drifts (Mann–Kendall, p < 0.01, with Sen's slope and weeks-to-limit). A CUSUM change-point estimate dates when a confirmed drift began. Confirmed drifts also alert in the daily checks. It has its own Weekly review screen, an overview card, and a "Weekly system" column in the replay. |
| **Mission replay** (`replay.js`) | Replays days 90–147 through the engine and measures early-warning lead time against fixed medical limits; hosts judge mode (`?judge`). |
| **EVA readiness** (`eva.js`) | GO / CAUTION / NO-GO before a spacewalk from alertness, sleep debt, symptoms, vitals, space weather, dose and airlock kit, with reasons and fixes. |
| **Live sensor** (`live.js`) | Any Bluetooth LE heart-rate strap/watch (standard Heart Rate profile): live HR, RR intervals and RMSSD vs your baseline; saves a resting reading. Simulator for browsers without Web Bluetooth. |
| **Blackout mode** (`blackout.js`) | Simulates loss of contact (e.g. 14-day solar conjunction): ground escalations reroute to the CMO, reports queue, countdown in the top bar. |
| **Crew cohesion** (`cohesion.js`) | "Connection with crew" check-in measure (a new behavioural indicator) and a private on-device journal. |
| **FHIR export** (`fhir.js`) | HL7 FHIR R4 Bundle — Patient, LOINC/UCUM-coded Observations and DetectedIssues — for ground medical systems. |
| **Settings** (`settings.js`) | Language (English, Français, Deutsch, 日本語, Русский, हिन्दी — navigation, headings and common controls), glove mode, voice control, install, and encrypted sync. |

**Offline install.** `manifest.webmanifest` + `sw.js` make HELIOS installable and usable with no connection (served over http/https).

**Encrypted sync.** `node tools/sync-server.js` runs a relay that only stores ciphertext.
- **Encryption:** each device encrypts with AES-256-GCM, using a key derived from the crew passphrase (PBKDF2, 210k iterations).
- **Channel id:** also slow-derived, so the relay can't cheaply guess the passphrase.
- **Passphrase:** held in memory only, never saved.
- **What syncs:** each bundle carries a stable person id. Your own devices merge record by record, with the newest entry winning. A crewmate's record is never merged into yours. The crew medical kit merges per item.
- **Light-time delay:** the relay can hold bundles back to simulate the Earth light-time delay.

**Voice control** uses the browser's speech recognition, which Chrome processes online — it is the one feature that needs a connection.

## Safety, privacy and accessibility

- **Urgent findings follow you.** Any Urgent finding (for example chest pain reported in a check-in) shows a sticky alert bar on every screen, with its protocol and triage, until it is acknowledged.
- **Privacy lock.** Settings → Privacy lock sets a PIN or passphrase (with a strength guide). Wrong attempts are limited across reloads, with doubling waits. The record is then stored only as AES-256-GCM ciphertext (key from PBKDF2-SHA-256, 310,000 iterations). The plain-text copy is removed, the app auto-locks after inactivity, and repeated wrong PINs are rate-limited. Forgetting the PIN means losing the data, so keep an exported backup. **Forgot PIN?** on the lock screen explains this and, after you type ERASE, wipes the encrypted record so you can start fresh and restore a backup.
- **Hardened input.** Saved data, restored backups and synced bundles all pass through a sanitizer (`js/sanitize.js`). Unknown keys are dropped, text is bounded, and numbers and dates are validated, so a malformed or hostile file can't crash the app or inject markup. Profile text is also escaped wherever it is shown.
- **Resilient storage.** Older or damaged saved data is normalised on load. A failed save (full or blocked storage) is reported instead of silently lost. A screen that throws shows a recoverable message instead of a blank page.
- **Accessibility.** Text colours meet a 4.5:1 contrast ratio. Dialogs trap focus and close with Escape. Page changes are announced to screen readers, and every trend chart has a table view. Blur effects are dropped when the system asks for reduced transparency, and on phones for performance.
- **Guided tour** on first run (replay from Settings or the command palette).
- **Exports.** Any indicator as CSV from Trends, and all your readings as a re-importable CSV from My profile.

## Detection benchmark: fewer false alarms

`tools/benchmark.js` generates randomized simulated astronauts:
- **Between-person spread:** taken from real MMASH data.
- **Realistic noise:** day-to-day noise is autocorrelated (AR(1), φ = 0.5).
- **Personal baselines:** 10 preflight readings each.
- **Problems:** 40 % stay healthy. The rest develop problems with random indicator, onset, speed and size.

Detectors run in real time. Variants were compared on seeds 1–200, and the chosen one was confirmed on unseen seeds 1001–1200. Two scoring rules keep the comparison honest:
- **A detection must be a new alarm** that starts on or after the problem begins.
- **False alarms are counted twice:** as separate alarms, and as the share of time a healthy indicator spends in false alarm, so a stuck alarm can't hide.

| Detector (held-out people) | Caught | Median delay | False alarms / person-month | Time in false alarm |
|---|---|---|---|---|
| v1: 3-day mean ≥ 2 SD + 14-day line projection + all limits | 94.8 % | 8 d | 9.96 | 10.3 % |
| **v3 (shipped)** | **95.2 %** | **12 d** | **2.71** | **3.1 %** |

**What v3 does:**
- **Robust EWMA control chart:** λ = 0.2, limit widened for autocorrelation, each day's input capped at ±4 SD.
- **Same-day flag for sudden jumps** of 4 SD or more.
- **Weekly Mann–Kendall trend test** for slow drifts.
- **Action and urgent limits always alarm.** Population monitoring limits alarm only while no personal baseline exists. Exercise thresholds are treated as a prescription *target*, enforced only for someone whose normal meets them.

> **Correction.** An earlier version of this README claimed the previous detector (v2) caught 98.8 % of problems. That figure came from a scoring flaw: an alarm already running before a problem began was counted as detecting it. Re-scored, v2 caught 72 %, and its weekly CUSUM test kept healthy indicators in false alarm 29 % of the time. CUSUM latches onto the small error any estimated baseline has. v3 removed CUSUM from alerting; it now only estimates when a confirmed drift began.

**Also tested:**
- **Sparse measurements** (weekly labs and scans, `--sparse`). No rule dominated. The current rule (94 % caught, 2.0 false alarms per month) stays the default. A confirm-twice rule (90 %, 0.97 a month) is what the Conservative setting uses.
- **Problems spanning several measurements** (`--syndromes`, e.g. sleep loss moving sleep, reaction time and mood a little each). A combined pattern score added 1.2 points of detection for about 11 % more false alarms. It's adopted only where no single measurement has alarmed.

The benchmark is simulation: it shows how the detector behaves under realistic noise, not clinical performance. Real-data results follow.

```bash
node tools/benchmark.js 200 "v1: original daily engine|HELIOS engine (as shipped, v3)"
node tools/benchmark.js --sparse
node tools/benchmark.js --syndromes
```

## Validation on real multi-week data (PMData)

HELIOS was run on **16 real people over about 5 months**: daily Fitbit resting heart rate, sleep and very-active minutes, daily self-reported mood and stress, and weight and fluid logs.
- **Setup:** each person's first 30 days served as their baseline, and the remaining ~4 months were judged day by day.
- **Data:** only the small daily files (≈ 9 MB) are fetched, each checked against OSF's published SHA-256.

```bash
node tools/fetch-pmdata.js && node tools/pmdata-check.js
```

| 16 people, ~4 months each | v1 | v3 |
|---|---|---|
| Alerts per person per month | 7.2 | **2.1** (−72 %) |
| Share of time an indicator is alerting | 35.6 % | **6.3 %** (−82 %) |

**What the real data taught us:**
- **The exercise prescription was wrongly enforced as a safety limit.** Ordinary people stayed in alert 74–90 % of the time until it became a target. That's now fixed.
- **CSV parsing:** PMSys files contain quoted lists that break naive CSV splitting. HELIOS's own parser handles them.
- **Scale coding:** 0 means "not answered", and stress is coded 5 = relaxed (verified from its +0.45 correlation with mood).

These are healthy people living normal lives (colds, holidays, training), so not every alert is false. The alerts did not cluster around the 77 reported minor sports injuries, which is expected, because those don't change these measures.

*PMData: Thambawita V. et al., "PMData: a sports logging dataset", ACM MMSys 2020, https://doi.org/10.1145/3339825.3394926, licensed CC BY 4.0. The raw data is not redistributed here.*

## Validation on real wearable data (PhysioNet MMASH)

HELIOS's sensor and import code was run on **real 24-hour recordings from 19–22 healthy adults**: beat-to-beat intervals from a chest strap, per-second heart rate from an activity monitor, and sleep logs.

```bash
node tools/fetch-mmash.js     # downloads ~25 MB, verifies SHA-256, extracts (never committed)
node tools/mmash-check.js     # runs HELIOS's own code on it
```

| Check | Result |
|---|---|
| Bluetooth heart-rate packets → HELIOS decoder | Round-trip error ≤ 0.48 ms, within the protocol's 1/1024 s resolution |
| Live HRV (RMSSD) vs a reference computation | r = 0.98, mean absolute difference 1.6 ms, on 19 nights |
| Noisy recording (31 % artefacts) | Flagged as too noisy (66 % clean beats) instead of reporting a wrong value |
| Resting HR: chest strap vs activity monitor | Median difference 0.5 bpm |
| Real sleep files through the CSV importer | 21 of 21 imported with correct hours; the one empty file was rejected cleanly |
| Real people vs HELIOS's default ranges | 6 of 19 outside the default resting-HR band and 8 of 19 outside the HRV band. That's why HELIOS learns each person's own baseline. |

This testing found and fixed four bugs:
- HRV was inflated by artefacts (the old filter compared each beat only with the previous one and counted differences across removed beats).
- HRV had no quality gate for noisy straps.
- Day-numbered dates ("1", "2") were silently parsed as real dates in 2001.
- Spreadsheet date serials became the year 45123.

Each recording covers about one day, so this validates the sensor, HRV and import paths, not multi-week trend detection.

*MMASH: Rossi A., Da Pozzo E., Menicagli D., et al. "Multilevel Monitoring of Activity and Sleep in Healthy People" (v1.0.0), PhysioNet (2020), https://doi.org/10.13026/cerq-fc86. The data is licensed under the Open Data Commons Open Database License v1.0, and these results are a Produced Work from it. The dataset itself is not redistributed in this repository.*

## Personalization: HELIOS adapts to you

Open **My profile** (or click **Make it mine** on the dashboard) to create your own profile. HELIOS
then judges every reading against *your* normal instead of a population average. The demo crew stay
available in the crew menu.

- **Your data in.** Log readings in the daily check-in (sleep, resting HR, HRV, blood pressure,
  temperature, exercise, mood, stress, symptoms) and take the alertness test. You can also import a
  CSV with a `date` column plus any indicator IDs (`rhr`, `hrv`, `sbp`, `sleep`, `pvt`, …). The
  profile page has a template.
- **Preflight baseline.** CSV rows dated before your mission start, or values typed in during
  setup, become your preflight baseline.
- **Learns, then adapts.** Without preflight data, HELIOS calibrates from your first 7 readings.
  After that the baseline adapts slowly: a 30-day half-life over readings more than 14 days old,
  skipping outliers. The 14-day lag means a developing problem doesn't quietly become your new normal.
- **Realistic spread.** Your spread is blended with the population reference (4 pseudo-readings),
  so a handful of readings can't produce an unrealistically tight band.
- **"This is normal for me."** Re-baselines one indicator on your last 14 days (logged, and
  reversible).
- **Alert sensitivity.** Choose Sensitive, Standard or Conservative. This moves the daily detector's smoothed alert level (2.75 / 3.25 / 3.75). For weekly lab values, Sensitive and Standard use 1.5/2.5 and 2/3 SD, and Conservative waits for confirmation (one result ≥ 2.5 SD, or two in a row ≥ 1.5 SD).
- **Private by design.** Everything stays in this browser. You can export a backup, restore it, or
  delete your profile and data.

## Health domains and indicators

- **Cardiovascular**: resting HR, HRV (RMSSD), systolic BP
- **Bone & Muscle**: estimated hip BMD change (vs. the expected in-flight curve), urinary calcium, countermeasure exercise, grip strength
- **Immune**: lymphocytes, CRP, salivary EBV/VZV shedding, core temperature
- **Radiation**: daily dose rate, career dose with a projection to mission end against the 600 mSv limit
- **Sleep & Behavioral**: sleep duration and efficiency, mood, stress, PVT reaction time
- **Neuro-ocular (SANS)**: retinal nerve-fiber-layer change (OCT), headache days
- **Habitat**: ppCO₂, temperature, humidity, sleep-station noise (shared exposures that often explain symptoms)

## How assessment works (`js/engine.js`)

1. **Personal baseline.** Deviation in SD from the astronaut's preflight mean (or from an expected in-flight trajectory for bone loss). 2 SD → *Monitor*, 3 SD → *Action*.
2. **Absolute limits.** Medical thresholds per indicator (*Monitor / Action / Urgent*).
3. **Trend.** Linear trend over 21+ days, projected 14 days ahead, so slow drifts are caught before they cross a limit.
4. **Rules.** These combine indicators and symptoms into findings. For example, sleep loss together with slower PVT gives "Sleep loss is slowing your reactions", and headaches together with high cabin CO₂ point to the scrubber fault. Each finding lists its evidence, the steps to take, a linked protocol and a recommended route: self-manage, CMO, flight surgeon, or immediate crew response.
5. **Readiness** is 100 minus capped penalties for each domain.

## Validation on real astronaut data

`tools/evaluate.js` tests the detection methods on open clinical data from the four
**SpaceX Inspiration4** crew, taken from NASA's Open Science Data Repository:

- complete blood count (OSD-569)
- metabolic panel, serum cardiovascular panel and serum immune panel (OSD-575)

Each crew member has 7 blood draws: 3 preflight and 4 post-flight. The raw CSVs are in `data/osdr/`.

**Task:** using each person's own preflight draws as the baseline, single out the draw taken the
day after landing (R+1) from normal draws. Normal draws are the recovery draws, plus each preflight
draw scored against the other two. That gives 4 positives and 24 negatives.

**Method:** leave-one-crew-out. The held-out person is never used to fit SDs, select features,
train weights or set thresholds.

```bash
node tools/evaluate.js   # writes data/validation.json and js/validation-data.js
```

| Run 3 (blood count + metabolic panel, corrected) | AUROC | AUROC (post-flight only) | R+1 ranked first |
|---|---|---|---|
| Clinical reference ranges | 0.44 | 0.45 | 1 / 4 |
| HELIOS rules (personal baseline, ≥3 SD) | 0.34 | 0.38 | 0 / 4 |
| Unsupervised anomaly score | 0.35 | 0.40 | 0 / 4 |
| **Spaceflight-signature model** | **0.79** (p = 0.037) | **0.92** | **3 / 4** |
| Logistic regression (L2) | 0.73 | 0.88 | 3 / 4 |

**Final models.** Run 3 above was hand-picked, so two follow-ups test that choice more fairly:

| Final model | AUROC | AUROC (post-flight only) | R+1 ranked first |
|---|---|---|---|
| **Ensemble:** rank-average of all 24 configurations (3 panel sets × 2 models × 4 feature counts) | **0.85** (p = 0.012) | **0.96** | **3 / 4** |
| **Nested search:** best of the 24 chosen by inner leave-one-crew-out on the training crew only | 0.68 (p = 0.15) | 0.65 | 1 / 4 |

The nested search is the most honest estimate of picking one "best" model. It scores lower than the
hand-picked run 3 because, with 4 people, which configuration wins is mostly noise. Averaging the
configurations avoids that, but the ensemble was designed after runs 1–3, so treat it as promising
rather than proven.

Run 1 (all 113 lab values, chosen before seeing any results) peaked at an AUROC of 0.64. Runs 2–3
were added after looking at run 1, so their scores are optimistic. With 4 people, no result is
significant once corrected for multiple comparisons. At the threshold learned on the other crew,
sensitivity is 0–25%, so the models rank well but are not calibrated for alarms. The app's
**Model validation** page shows every run.
